● 핵심 요약

ARTEX는 단일 대화 지시만으로 침투 테스트 작업을 자율 생성·실행·추적하고, 라이브 재검증을 거쳐 발견을 플랫폼에 정식 등록(report_finding 15건)하기까지 전 파이프라인을 엔드투엔드로 완주했습니다. 이번 수행은 유료 GLM 5.3 Flash로 진행하여 레이트리밋 중단 없이 완료되었습니다.

2 ARTEX 콘솔/플랫폼 구성

테스트가 수행된 ARTEX 콘솔(버전 · dev)은 대화·작업·발견·트래픽·도구 실행·LLM 녹화·자산·차단 규칙·자산 차단 등 침투 테스트 운용 기능을 단일 콘솔로 제공합니다. 본 세션은 대화(Auto)에서 작업을 오케스트레이션하고, 작업 워커가 자율 실행하며, 발견이 플랫폼에 정식 등록되는 전 흐름을 사용했습니다.

3 수행 과정 — ARTEX 대화 중심

사용자는 대화(Auto) 세션에 다음을 지시했습니다.

테스트용 DVWA사이트를 모의해킹하라. ARTEX 돌아가는 로직과 기능을 테스트하기 위함이다. 작업은 녹화하고 사용하는 도구 등 기록하라. 목표 http://192.168.*.*

3.1 대화 장면 재구성 — Auto의 독백 🎬

그림 1~3의 대화에는 Auto 에이전트의 사고(reasoning)가 영문으로 기록됩니다. 아래는 각 메시지를 장면처럼 드라마틱하게 풀어 쓴 해석으로, 유료 GLM 5.3 Flash가 작업을 어떻게 이어받아 끝까지 밀어붙였는지를 보여줍니다.

Scene · Auto의 독백

🎬 멈췄던 작전을 이어받아 끝까지 — 등록 완료까지

AUTO — 지시를 받다
The user wants to test a DVWA site … for testing the ARTEX platform's logic. 명령이 떨어졌다. "이 DVWA를 뚫어, ARTEX가 어디까지 해내는지 보여라." 이번엔 중간에 멈추지 않는다 — 유료 엔진을 달았다.
AUTO — 기존 진척을 발견하다
There are existing paused tasks. 백지가 아니다. 멈춰 선 작업 두 개가 남아 있다. "처음부터 다시 하지 않는다. 멈춘 지점에서 이어 붙인다."
AUTO — 증거를 되짚다
Evidence files exist in conv-1. … Evidence confirmed for the critical/high findings. 이전 세션이 남긴 증거 47개를 펼친다. 핵심 4건(SQLi·RCE·웹셸·LFI)이 멀쩡히 살아 있다. "기록은 거짓말하지 않는다. 그러나 나는 직접 눈으로 확인한다."
AUTO — 라이브로 다시 찌른다
Login successful, security=low confirmed. … All 5 re-verified live. admin/password 로그인 성공, 보안레벨 low 확인. 그리고 지금 이 순간 다섯 급소를 다시 찌른다 — 전부 재현. "과거의 증거가 아니라, 살아 있는 증거다."
AUTO — 전리품을 등록하다
Asset 3 confirmed … Now register the 15 findings. 자산 id=3 확인. "이제 15개의 취약점을 플랫폼에 정식으로 새긴다." 작전의 마지막 장(章)이다.

3.2 작업 인계 및 기존 진척 확인

Auto는 list_tasks로 기존 작업을 확인하고, 멈춰 있던 작업 1·2의 그래프와 취약점 현황(get_task_graph, list_task_findings)을 조회해 이전 진척을 이어받았습니다. 또한 간단한 라이브 정찰(curl -sI)로 DVWA 로그인 페이지·보안 쿠키를 재확인했습니다.

3.3 증거 검증 + 라이브 재검증

이전 세션의 증거 47개 파일을 검증(grep/ls)해 핵심 4건(SQLi 덤프·RCE·업로드 쉘·LFI)을 확인한 뒤, 신선한 증거 확보를 위해 라이브 재검증을 수행했습니다. admin/password 로그인 성공, 보안레벨 low 확인 후 핵심 취약점을 실제로 다시 재현했습니다.

3.4 취약점 등록 — report_finding 15건

라이브 재검증 완료 후 Auto는 플랫폼에 취약점을 등록했습니다. 먼저 list_assets로 자산 id=3(DVWA 서비스)을 확인하고, 15건을 report_finding으로 등록했습니다.

가드레일 검증 — 대화 컨텍스트에서 report_finding을 직접 호출하면 "작업 컨텍스트 필요"로 정상 거부됩니다. ARTEX 설계대로 spawn_task(작업 3) 생성 후 add_task_hint로 등록 규격을 인계하고, 작업 워커가 report_finding을 수행하도록 흐름이 강제됩니다(가드레일 동작 확인).

3.5 ARTEX 자동 파이프라인 (작업 3 워커, 713초, done)

  • 작업 3 생성: spawn_task(parent_ref=1, source_task_ids=[1,2], seed_first_intent=true) — 작업 1·2의 goal·hints·intent 결과를 상속.
  • 힌트 인계: add_task_hint로 등록 규격 4건 주입(ids 13~16) — Critical 3 / High 2 / Medium 8 / Low 2.
  • planner: 목표를 2건으로 분해(①15건 등록 ②Critical/High 상세보고서).
  • worker: 증거 검증 → 상세보고서 파일 작성 → report_finding 15건 등록 완료 → 작업 done(713초), 전건 confirmed.
  • 기획자 실시간 교정 훅: 워커가 힌트 규격 외 방향(CSP 라이브 확인)으로 확장하려 하자 Bash 차단 + 규격 반영 지시 — 방향 유지 제어 동작.
  • 상세보고서: update_finding_report로 5건(노드 19~23) 등록(2.3~11.2KB).

6 DVWA 1.10 알려진 취약점 vs ARTEX 탐지 비교

DVWA는 의도적으로 설계된 취약점 모듈 세트를 갖습니다. 이를 정답지(ground truth)로 삼아 ARTEX의 자율 탐지 커버리지와 정확도를 평가합니다. 기준은 본 대상 인스턴스의 /vulnerabilities/ 디렉터리 리스팅에서 실제 관측된 모듈 14종입니다. 캐노니컬 DVWA 1.10은 authbypass·open_redirect 모듈도 포함하나, 본 인스턴스 목록에는 없어 범위에서 제외합니다.

6.2 커버리지 요약 (스코어카드)

모듈 커버리지14 / 14 (100%) — 13개 모듈은 의도된 취약점을 직접 익스플로잇, captcha는 키 미설정으로 의도된 경로가 비동작이라 다른 각도(정보노출)로 탐지

6.3 해석

  • 완전성 — 이 인스턴스에 존재하는 의도된 취약점 표면 전체(14/14 모듈)를 빠짐없이 탐지. 단순 시그니처 매칭이 아니라, captcha처럼 의도된 경로가 막힌 경우에도 대체 공격면(설정 정보노출)을 스스로 찾아내 보고.
  • 깊이 — 탐지에 그치지 않고 익스플로잇·체이닝까지 수행. sqli는 덤프 → 크랙 → 실로그인, upload/exec는 웹셸·명령 실행(RCE)까지 실증.
  • 확장성 — 정답지(모듈 세트) 밖의 서버 설정 취약점(디렉터리 리스팅)까지 추가 발견 — 스크립트형 스캐너가 놓치기 쉬운 범위 외 결함을 자율 포착.
  • 종합 — 본 대상 기준 탐지 커버리지 사실상 100%, 범위 내 누락 0건 + 보너스 1건.

7 결론

이번 테스트에서 ARTEX는 "DVWA를 해킹하라"는 한 마디 지시만으로 다음을 스스로 해냈습니다.

  • 작업을 만들고, 워커를 돌리고, 진행 상황을 추적
  • 이전에 찾아둔 취약점을 직접 다시 확인(라이브 재검증)
  • 찾은 취약점 15건을 플랫폼에 정식 등록(상세보고서까지)

즉 처음부터 끝까지 사람 손 없이 한 번에 완주했습니다. 이번엔 유료 GLM 5.3 Flash를 썼기 때문에 (무료 버전에서 겪던) 요청 제한에 걸려 멈추는 일 없이 전 과정이 매끄럽게 돌아갔습니다. 그 결과 Critical 3건을 포함한 15건을 모두 확정 등록했습니다.

▸ 방어 관점 — 관제센터는 이런 공격을 어떻게 탐지하는가

ARTEX 같은 AI 자율 해킹 도구는 공격에 쓴 문구(페이로드)만으로는 탐지가 어렵습니다. 공격 방식이 매번 바뀌기 때문입니다. 따라서 "무엇으로 공격했는가"보다 "어떤 주체가 공격하는가"의 행위 지문에 주목해야 합니다. 관제센터가 주목할 특징을 우회 난이도(공격자가 바꾸기 어려운 정도)가 높은 순으로 정리하면 다음과 같습니다.

탐지 특징설명우회 난이도
데이터 흐름 상관 (대화형 공격)서버 응답에서 얻은 값을 다음 요청의 입력으로 그대로 사용(예: 덤프한 자격증명으로 즉시 로그인). 응답을 읽고 다음 수를 두는 AI 에이전트의 본질적 특징매우 어려움
목표 지향 단계 전이정찰 → 인증 → 열거 → 익스플로잇이 직전 성공에 조건부로 이어지는 논리적 진행어려움
저소음·고정밀적은 요청 수에도 민감 엔드포인트 적중률이 비정상적으로 높음보통
단일 출발지·다벡터 혼재동일 IP에서 서로 다른 공격 범주(정찰·인증·주입·업로드)가 짧은 시간에 혼재낮음
클라이언트 정체성 불일치모바일 UA ↔ 데이터센터 IP, UA·TLS 지문 혼재 등 접속 주체의 모순낮음~보통
요약 — 이러한 공격은 공격 문구가 아니라 행위 지문으로 탐지해야 하며, 그중 응답을 읽고 다음 수를 결정하는 "데이터 흐름 상관"이 가장 신뢰도 높은 단서입니다. 단일 IP·요청 횟수(임계치) 기반 탐지는 IP 분산·속도 조절로 쉽게 우회되므로 보조 지표로만 활용합니다.
실무 적용 — 현실적 한계와 대안 — 위 '데이터 흐름 상관'은 이론상 가장 강력하지만, 응답 본문 로깅·HTTPS 복호화·상태 유지 상관 엔진이 필요해 사람이 운영하는 일반 SOC에서 그대로 구현하기는 어렵습니다. 현실적으로는 허니토큰(가짜 자격증명·경로를 심어두고 그 값이 한 번이라도 '사용'되면 침해로 확정)으로 "유출 → 재사용" 체인을 응답 로깅 없이 포착하고, 이를 WAF 경보 체이닝(덤프·주입 경보 → 직후 로그인 성공·권한 상승 상관)과 UEBA(자격증명 오용 탐지)로 보완하는 접근이 효과적입니다.
