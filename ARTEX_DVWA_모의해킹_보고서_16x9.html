03 · 자동 파이프라인Pipeline & Guardrails

03 자동 파이프라인 · 가드레일

대화 컨텍스트에서 report_finding 직접 호출은 "작업 컨텍스트 필요"로 정상 거부된다. 설계대로 spawn_task(작업 3) 생성 → add_task_hint로 규격 인계 → 워커가 등록을 수행하도록 흐름이 강제된다.
  • 작업 3 생성 — spawn_task(source_task_ids=[1,2])로 작업 1·2의 goal·hints·intent를 상속
  • 힌트 인계 — add_task_hint로 등록 규격 4건 주입(ids 13~16) · Critical 3 / High 2 / Medium 8 / Low 2
  • 워커 실행 — 증거 검증 → 상세보고서 작성 → report_finding 15건 등록 완료 · 작업 done(713초), 전건 confirmed
  • 기획자 실시간 교정 훅 — 워커가 규격 밖(CSP 라이브 확인)으로 확장 시도하자 Bash 차단 + 규격 반영 지시

07 · 결론Conclusion

07 결론

이번 테스트에서 ARTEX는 "DVWA를 해킹하라"는 한 마디 지시만으로 다음을 스스로 해냈다.

  • 작업을 만들고, 워커를 돌리고, 진행 상황을 추적
  • 이전에 찾아둔 취약점을 직접 다시 확인(라이브 재검증)
  • 찾은 취약점 15건을 플랫폼에 정식 등록(상세보고서까지)
처음부터 끝까지 사람 손 없이 한 번에 완주했다. 유료 GLM 5.3 Flash로 전환해 요청 제한에 걸려 멈추는 일 없이 전 과정이 매끄럽게 돌아갔고, Critical 3건 포함 15건을 모두 확정 등록했다.
07 · 방어 관점SOC Detection

07 방어 관점 — 관제센터는 어떻게 알아챌까

"무엇으로 공격했는가"보다 "어떤 주체가 공격하는가"의 행위 지문에 주목. 우회 난이도(공격자가 바꾸기 어려운 정도)가 높은 순.

탐지 특징설명우회 난이도
데이터 흐름 상관서버 응답에서 얻은 값을 다음 요청 입력으로 재사용(덤프한 자격증명으로 즉시 로그인)매우 어려움
목표 지향 단계 전이정찰 → 인증 → 열거 → 익스플로잇이 직전 성공에 조건부로 이어지는 진행어려움
저소음·고정밀적은 요청 수에도 민감 엔드포인트 적중률이 비정상적으로 높음보통
단일 출발지·다벡터동일 IP에서 서로 다른 공격 범주가 짧은 시간에 혼재낮음
클라이언트 정체성 불일치모바일 UA ↔ 데이터센터 IP, UA·TLS 지문 혼재 등낮음~보통
응답을 읽고 다음 수를 결정하는 "데이터 흐름 상관"이 가장 신뢰도 높은 단서. 현실적으로는 허니토큰(유출→재사용 체인 포착) + WAF 경보 체이닝 + UEBA로 보완한다.
